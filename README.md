# A.R.I. — Audiological Roaming Intelligence

A minimalist generative street-music web experience. An isometric neon android roams the grid with a wearable synth rig, building music on the spot while visitors, voices and street events appear around the performance.

**Live demo:** https://nachtaap.github.io/A.R.I/  
**Best experienced with sound on.**

![A.R.I. preview](icon-512.png)

> **Unofficial fan tribute.** A.R.I. is inspired by ARIatHOME and the idea of spontaneous street collaboration. It is not affiliated with, endorsed by, or connected to ARIatHOME. No recordings, samples, footage, names or likenesses from ARIatHOME are used. The audio and visuals are generated by the project itself.

## What A.R.I. is

A.R.I. is not a playlist and not a conventional DJ simulation.

The project combines two layers:

1. **A musical score engine** that composes a complete musical identity for a track.
2. **A live street runtime** that surrounds that score with A.R.I., guests, audience simulation, visual feedback and procedural events.

The goal is to make the music feel authored rather than assembled from interchangeable layers. Genre should be audible in rhythm, bass behaviour, harmony, phrasing and sound design — not only in BPM or labels.

## Current music architecture

The current musical foundation is the same score engine used by the internal **Musician Lab**.

The score path is:

**musician profile → ARIComposer → score events → ARIScoreSynth → A.R.I. runtime**

This replaces the older approach in which the main live runtime independently generated drums, bass and harmony from several overlapping systems.

### ARIComposer

`ari-composer.js` is the authoritative composition engine.

It generates a deterministic score from:

- a seed;
- a genre family;
- a musician identity;
- tempo;
- rhythm grammar;
- bass role;
- harmony role;
- instrument voices;
- arrangement form;
- swing and timing characteristics.

The composer uses separate deterministic random streams for musical roles such as drums, harmony and melodic density. A given profile + seed therefore produces a reproducible musical result.

The generated score contains explicit timed events for:

- kick;
- snare;
- hats;
- percussion;
- bass;
- chords;
- lead.

It also defines the track form, harmony, scale, root, musical identity and per-section structure.

### ARIScoreSynth

`ari-score-synth.js` is the renderer for those score events.

It synthesizes every voice in the browser with Web Audio. The score synth includes distinct rendering paths for percussion, sub and synth basses, Reese-style basses, keys, organs, plucked sounds, bells, pads and other tonal voices.

There are no prerecorded drum loops or sample packs in this path.

### Melody baseline

The current musician profiles use:

**Melody density = 0%**

This is intentional.

During development, the strongest and most genre-recognizable beats consistently came from the rhythm, bass and harmony systems without an automatically generated lead melody over the top.

The melody architecture remains available for later deliberate use, but it is not part of the current baseline accompaniment.

## Musician Lab

`musicians.html` is an internal development and feedback tool rather than part of the public-facing experience.

The Musician Lab contains one fictional musician per genre family. Each musician is a reproducible musical profile rather than a cosmetic character.

Current families include:

- techno;
- jazz;
- breakbeat;
- hip-hop;
- trap;
- R&B;
- soul;
- funk;
- house;
- UK garage;
- drum & bass;
- bass;
- trance;
- afro;
- reggae / dub;
- Latin;
- ambient;
- pop;
- rock;
- experimental.

Each profile controls parameters such as:

- tempo;
- swing;
- kick weight;
- kick attack;
- drum drive;
- bass level;
- chord level;
- melody density.

The profile also defines deeper musical identity such as rhythm grammar, bass role, bass voice, harmony role, keys voice, lead voice, kit, mode and timing behaviour.

### Listening versions

The Musician Lab renders an eight-bar listening version from the main section of the score.

The process is:

1. choose musician;
2. choose or enter a seed;
3. compose a score with `ARIComposer`;
4. render the score through `OfflineAudioContext`;
5. synthesize it with `ARIScoreSynth`;
6. expose the rendered result as a WAV-backed browser Blob;
7. A/B the current profile against an adjustment.

The same seed can therefore be used for controlled comparisons.

### Feedback workflow

The lab can export a JSON file containing:

- musician;
- engine version;
- profile version;
- seed;
- active settings;
- musical identity;
- recognition rating;
- energy rating;
- listening-interest rating;
- written notes.

This makes feedback reproducible instead of relying on descriptions such as “the previous techno beat”.

## Musician profiles

`ari-musicians.js` is the musician registry and profile layer.

The initial design uses one musician per genre family. The registry is deliberately structured to support multiple musicians per family later.

The long-term idea is that A.R.I. can express different moods through different musicians within the same genre rather than treating a genre as one fixed preset.

A musician therefore represents a musical point of view.

## Score bridge

`ari-score-bridge.js` connects the new score engine to the existing A.R.I. street runtime.

When a new A.R.I. track is created, the bridge:

1. maps the selected/current A.R.I. genre to a musician family;
2. loads the musician profile;
3. forces the current baseline melody density to zero;
4. composes a deterministic score;
5. installs that score as the track's musical form;
6. plays score events through `ARIScoreSynth`.

While score mode is active, the legacy runtime no longer independently adds its own competing accompaniment.

The existing street layer remains available for things such as:

- A.R.I. performance behaviour;
- guests;
- vocals;
- visitor events;
- audience simulation;
- locations;
- camera events;
- battery events;
- visual feedback;
- operator controls.

This keeps the street experience while giving the accompaniment one clear musical source of truth.

## Street Improv and genre resolution

`ari-v108.js` still provides the broad request/style vocabulary and genre-resolution layer.

The project contains a large number of canonical style identities and alternate request names. These let free-form genre requests resolve toward a usable family or stylistic direction.

The important architectural change is that genre resolution and musical composition are now separate responsibilities:

**request / style identity → musician family → score composer**

The old Street Improv accompaniment logic is no longer the preferred final source for the core beat when score mode is active.

## Guests and A.R.I.

A.R.I.'s street layer can still introduce guests and performance behaviour around the composed accompaniment.

Guests may use voices or synthesized instruments. Existing runtime systems can provide call-and-response, visitor interaction and A.R.I.'s own vocal behaviour without replacing the underlying score.

This separation is deliberate:

**the score establishes the groove; the street runtime reacts to it.**

## Mini-Freestyler (rap + jazz vocals)

`ari-mini-freestyler.js` + `ari-mini-freestyler-data.js` provide POCKETFLOW-style guest/A.R.I. vocals on top of the score.

- **Rap** (hip-hop / trap families): event prosody v0.2 — microtiming, energy emphasis, strong/tail chord resolution.
- **Jazz**: continuous phrases from warm-clean v1.4 — major-first cells, swing, stable resolve; transposed to the score’s parent major.
- Planning is deterministic from the score seed + baked performance data (no remote inference, no source audio).
- Rendering runs in a Web Worker; the main thread only schedules buffers on the transport grid.
- When active, `track.miniFreestylerOwnsVocals` is set so legacy vocal brains should not double-sing.

Vocals react to the score; they do not replace ARIComposer / ARIScoreSynth.

### Script order (vocals)

```html
<script src="./ari-mini-freestyler-data.js"></script>
<script src="./ari-mini-freestyler.js"></script>
<script src="./ari-score-bridge.js"></script>
```

Load data before the engine, and both before the score bridge.

## Audience simulation


A.R.I. includes a simulated audience model used by the hidden Live Signal operator view.

Listener archetypes have values such as:

- engagement;
- activity;
- retention;
- positivity.

These values drive the radar visualization and corresponding listener rows.

The audience radar is therefore a visualization of simulated internal data rather than a decorative animation.

## The street

The music exists inside a reactive procedural SVG scene.

A.R.I.:

- carries a wearable synth rig;
- roams a fictionalized NYC-inspired street grid;
- reacts visually to musical events;
- can be joined by visitors;
- changes location;
- exposes live track information;
- includes occasional runtime events such as camera reversal and battery swapping.

A.R.I. itself remains the main play/pause control. Clicking or tapping the robot starts or pauses the performance. Space performs the same action when keyboard focus is not inside another interactive control.

## Public interface

The public interface remains intentionally sparse.

### Identity

The top-left identity includes:

- **A.R.I.**
- **Audiological Roaming Intelligence**
- live NYC time/weather where available;
- the small **inspired by ARIatHOME** tribute.

### Track information

The track area prioritizes:

1. track title;
2. genre / key / BPM.

BPM influences the metadata accent colour.

The public interface avoids exposing development detail unless the operator view is opened.

## Live Signal operator view

Press **Shift+D** to open the hidden operator panel.

The overlay is a wide, centered, neon-styled development console rather than the older tall inspector.

It contains:

- current runtime/track information;
- next-bars signal grid;
- audience radar;
- track character;
- instrument/interaction information;
- event-test controls.

### Event controls

The operator view can trigger existing runtime events directly:

- new track;
- new location;
- A.R.I. mic;
- reverse camera;
- battery swap;
- **export → ableton**.


The Musician Lab is a development surface; it is not intended as part of the public experience.

## Ableton export

The Live Signal view includes **export → ableton**.

The exporter generates a ZIP containing:

- a multitrack Standard MIDI File;
- isolated drums MIDI;
- isolated bass MIDI;
- isolated chords MIDI;
- isolated lead MIDI;
- A.R.I. vocal-guide MIDI;
- `track-info.json`;
- a small export README.

The export is intended as a bridge into Ableton Live for further production.

The current exporter transfers composition/MIDI information rather than browser-synth audio stems.

As the score-engine migration continues, export logic should increasingly use the authoritative score representation rather than reconstructing musical information from legacy runtime structures.

## Interactive rig and memory

`ari-discoveries.js` contains interactive rig behaviour and short-term street memory.

Rig controls can add live synthesized gestures without stopping the track. A short musical phrase can be remembered and referenced later by A.R.I.

The pink heart stores track-related memory locally in the browser.

No account is required for this local memory.

## Additional sound systems

A.R.I. still contains several experimental or supporting sound modules:

- `ari-creature-synth.js`
- `ari-sound-worlds.js`
- `ari-beat-foundation.js`

These should be treated as supporting runtime layers rather than competing core accompaniment engines.

The rule for current development is simple:

> **Do not weaken or replace a strong Musician Lab beat with additional automatic layering.**

Effects, guests and events should add character without turning A.R.I. into a parody of itself.

## Project structure

The current architecture is layered:

- `index.html` — main scene, transport, legacy runtime and public UI;
- `ari-v108.js` — request/style resolution and Street Improv runtime extensions;
- `ari-composer.js` — authoritative deterministic score composer;
- `ari-musicians.js` — musician registry, profiles and settings;
- `ari-score-synth.js` — Web Audio renderer for score events;
- `ari-score-bridge.js` — connects score composition to the A.R.I. runtime;
- `musicians.html` — internal Musician Lab;
- `musicians.css` — Musician Lab styling;
- `musicians-workbench.js` — Musician Lab controls, A/B rendering and feedback export;
- `ari-musicians-link.js` — private operator access to the Musician Lab;
- `ari-discoveries.js` — interactive rig and short-term musical memory;
- `ari-creature-synth.js` — generated character/creature synthesis;
- `ari-sound-worlds.js` — additional sound-world and character material;
- `ari-beat-foundation.js` — supporting runtime systems, Live Signal overlay and Ableton export;
- `sw.js` — PWA application-shell caching.

## Script order

The score modules must exist before the score bridge is installed.

The relevant end-of-page loading order is:

```html
<script src="./ari-composer.js"></script>
<script src="./ari-musicians.js"></script>
<script src="./ari-score-synth.js"></script>

<script src="./ari-v108.js"></script>
<script src="./ari-discoveries.js"></script>
<script src="./ari-creature-synth.js"></script>
<script src="./ari-sound-worlds.js"></script>
<script src="./ari-beat-foundation.js"></script>

<script src="./ari-mini-freestyler-data.js"></script>
<script src="./ari-mini-freestyler.js"></script>

<script src="./ari-score-bridge.js"></script>
<script src="./ari-musicians-link.js"></script>
```

`ari-score-bridge.js` must load after the existing runtime extensions so it can become the final accompaniment route.

`ari-musicians-link.js` is UI-only and should load last.

## Running locally

There is no build step.

Serve the repository through localhost or HTTPS, for example:

```bash
npx serve .
```

GitHub Pages can host the PWA directly.

Because A.R.I. uses a service worker, cached JavaScript can survive a normal refresh. When application-shell files change, bump the cache identifier in `sw.js`.

During development, a hard refresh may be needed after deployment.

## Development principle

The current musical baseline came from listening rather than from architectural preference.

The Musician Lab produced beats that were substantially clearer and more convincing than the previous layered runtime. That result now defines the direction of the project.

The priority is therefore:

1. preserve the score engine's groove;
2. make genres audibly distinct;
3. keep automatic melody restrained;
4. add street interaction around the music rather than through it;
5. make changes surgically;
6. avoid broad rewrites when a proven musical path already exists.
